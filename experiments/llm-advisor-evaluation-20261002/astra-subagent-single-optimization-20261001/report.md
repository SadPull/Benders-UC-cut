# GPT-6 Astra 子代理单次优化试验

本次只运行一个 gpt-6-astra 子代理，未恢复整组实验。四份建议经原有修复流程后均可行，并且均改善原有成本。

## 输入与执行方式

- 输入为此前种子 17 第 15 轮的同一份优化上下文。system.txt 与 user.txt 的 UTF-8 字节哈希逐项核对一致。
- 使用 gpt-6-astra、max 推理；不继承此前聊天历史，只给冻结输入文件。约束子代理仅可读取指定输入、写出最终 JSON，不调用求解器、外部 API、其他代理或读取参考结果。
- 只有一次成功创建的子代理任务。启动前两次模型名拼写错误被工具拒绝，没有创建代理或生成候选。
- 子代理的基础系统指令、工具环境和消息角色封装与 HTTP API 不同；此工具不能设置 temperature，也未提供实际 token 用量。因此只能保证业务输入完全一致，不能视为所有运行条件严格相同。
- 没有额外设置 65,536 token 上限，也没有设置客户端等待期限。这不意味着推理无限。[官方模型页](https://developers.openai.com/api/docs/models/gpt-6-astra)标注最大输出 128,000 tokens；Codex 子代理实际单次额度未由工具返回。

## 优化结果

输入时最佳可行成本：**583,861.4308**。独立参考成本：**571,014.0519**。参考结果仅用于返回后的比较，没有提供给子代理。

|2: early_block_trim|572,496.4654|11,364.9654|0.2596%|

最佳为候选 3，成本 **571,753.3169**，降低 **12,108.1139（2.0738%）**，相对参考成本差 **0.1295%**。这个百分比不是研究算法的认证收敛 gap。

## 修复与物理验证

四份原始矩阵均为合法的 10×24 二元矩阵，但原始离散可行性检查均未通过。原有修复器对每份矩阵只改动同一个位：第 6 台机组第 24 小时由 0 改为 1。结果应归于 Astra 建议与同一修复流程的组合，不能表述为四份原始建议都直接可行。

修复后全部四份调度通过 low/base/high 三场景的供需平衡、备用、出力上下限、启动/停机容量、爬坡、初始条件和最小开停机时间检查。最大物理残差 **4.55e-13 MW**，最大成本核算残差 **3.49e-10**。所有候选均为历史缓存中没有的新调度。

完整成功验证使用 12 次连续调度求解；首次验证因脚本封装缺少场景名称而在第一候选的三个场景求解后中断。修复的是结果封装，原候选未修改、子代理未再次调用。累计本地调度求解为 15 次，失败日志保存在 validation-attempt1.log。没有 SA 调用，也没有额外模型请求。

## 与前两次同输入试验比较

|方式|观察耗时|输出|最终验证结果|
|---|---:|---|---|
|DeepSeek Chat Completions|472.39 秒|65,536 推理 token，零正文，截断|无候选|
|DeepSeek Responses|516.26 秒|65,536 推理 token，零正文，截断|无候选|
|GPT-6 Astra 子代理|约 280.67 秒|完整 JSON，4 个候选；token 用量不可用|4 个经修复后可行，最佳成本 571,753.32|

子代理时间从确认启动到候选文件写入计算，包含读取输入和写文件工具，但不含更早的启动开销；不是 API 净响应时间。成功的本地验证另耗时 8.12 秒，之前失败的验证及脚本修复耗时没有混入模型时间。不可据此作严格延迟排名。

这一次 Astra 产生了可用且更好的候选，前两次 DeepSeek 请求均未生成正文。这支持继续研究 Astra 的候选质量，但只有一次固定上下文试验，无法断言普遍优势或将差异归因于模型、额度、推理策略中的单一因素。
